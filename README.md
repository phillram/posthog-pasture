# PostHog Pasture 🦔

An interactive sandbox for exploring and testing the [PostHog](https://posthog.com) JavaScript SDK. Connect your PostHog project, fire events, toggle feature flags, trigger surveys, generate experiment data, and inspect everything in real time.

> **Debug mode is always enabled.** All PostHog SDK activity is logged to the browser console automatically.

## Tech Stack

| Layer | Technology |
|-------|------------|
| Framework | Next.js 16 (App Router) |
| UI | React 19, Tailwind CSS 4 |
| Analytics | posthog-js |
| Language | TypeScript 5 |
| Linting | ESLint 9 with eslint-config-next |

---

## Prerequisites

- [Node.js](https://nodejs.org/) v18 or later
- A PostHog account with a **Project API Key** — find it in PostHog → Settings → Project Details

## Setup & Authentication

### 1. Connect PostHog

On first load you'll land on the **Setup** page (`/`):

1. Paste your **Project API Key** (`phc_...`)
2. Select your **API host** — US Cloud or EU Cloud
3. Click **Connect & Continue**

The key is validated against PostHog's `/decide` endpoint before proceeding. An error banner appears if the key is rejected, with a direct link to your project settings. If validation is blocked by a network or CORS error, the app proceeds anyway — PostHog's SDK will log any key problems in the browser console. The key is stored in `localStorage` and is never sent anywhere except PostHog's ingestion endpoints.

> **API Key locations:**
> - US: https://us.posthog.com/settings/project-details
> - EU: https://eu.posthog.com/settings/project-details

### 2. Log In

The app uses a simple local auth system to generate realistic PostHog identity events.

| Method | How | PostHog events fired |
|--------|-----|----------------------|
| **Login** | Any username + password `test` | `pasture_user_logged_in` |
| **Guest** | Click "Continue as Guest" | `pasture_user_logged_in` |
| **Register** | Name + email + any password | `pasture_user_registered`, then `posthog.identify()` |

#### Apply feature flags on login

The login page includes an **"Apply feature flags on login"** toggle (off by default). When enabled, `$feature_flag_called` events are fired for every flag after authentication — useful for testing experiment exposure tracking. Feature flags are always loaded regardless of this setting.

## Event Naming Convention

All custom events generated by PostHog Pasture use a `pasture_` prefix to distinguish them from PostHog system events and your own application events:

| Event | Where fired |
|-------|------------|
| `pasture_user_logged_in` | Login / Guest login |
| `pasture_user_logged_out` | Logout |
| `pasture_user_registered` | Register |
| `pasture_button_clicked` | Dashboard Quick Events |
| `pasture_feature_used` | Dashboard Quick Events |
| `pasture_purchase` | Dashboard Quick Events / Experiments |
| `pasture_signup` | Experiments |
| `pasture_form_submitted` | Dashboard / Experiments |
| `pasture_checkout_started` | Experiments |
| `pasture_signup_started` | Dashboard Quick Events |
| `pasture_search` | Dashboard Quick Events |
| `pasture_experiment_started` | Experiments wizard |
| `pasture_experiment_completed` | Experiments wizard |
| `pasture_js_executed` | JavaScript Sandbox |

PostHog system events (`$pageview`, `$identify`, `$feature_flag_called`, `$exception`, etc.) are sent with their standard names.

### Dashboard (`/dashboard`)

The main workspace for firing events. Organised into sections:

#### Quick Events
One-click buttons for the most common event types. Hover any button to see the exact event name and JSON payload sent.

| Group | Buttons |
|-------|---------|
| Event Tracking | Button Clicked, Page Viewed, Feature Used, Purchase, Form Submitted, Sign Up Started, Search, Capture Pageview |
| Error Tracking | Error Occurred (`$exception`) |
| Session Replay | Start Recording, Stop Recording |

#### Product Analytics
- **Custom Event** — Send any event name with a freeform JSON properties payload
- **Super Properties** — Register properties that attach to every subsequent event. Supports register, unregister by key, and **Show Active Super Properties** to inspect current state

#### Error Tracking
- **Custom Exception** — Build a `$exception` event with message, error type (TypeError, ReferenceError, etc.), source file, and line number
- Toggle **"Throw real JS error"** to generate a genuine stack trace via `posthog.captureException()`
- **Quick Trigger Error** — One-click test exception

#### Feature Flags
- View all flags loaded from your PostHog project with their current values
- **Activate / Deactivate** boolean flags, **Switch** multivariate variants — all via client-side overrides
- **Reload Flags** / **Clear Overrides**

#### Experiments
- Manually override any flag key to a specific value and apply it client-side
- **Quick Override** — click any loaded flag to cycle its value
- **Clear All** — remove all overrides

#### Surveys
- **Load All Surveys** — fetch every survey in your project
- **Matching Only** — fetch only surveys that match the current user
- **Trigger** — render a popover survey directly on the page
- Each survey card shows type, question count, description, and an expandable question list

#### People & Groups
- **Identify User** — link the session to a distinct ID with optional JSON properties
- **Reset** — generate a new anonymous `distinct_id`
- **Group Identify** — associate the user with a group (company, project, etc.)
- **Check** — show current group associations inline
- **Person Properties** — set properties on the current person without re-identifying

#### Sandboxes
- **JavaScript Sandbox** — run arbitrary JS expressions. Results are captured as `pasture_js_executed` events; errors are captured as exceptions. Quick snippets include: User Agent, Screen size, Performance, Cookies, localStorage, Timezone, and more
- **PostHog Console** — run any `posthog-js` command like a browser console (`Cmd+Enter` to execute). Includes quick command buttons, a full command reference with documentation links, and a scrollable command history with "Reuse"

### Flags (`/flags`)

A dedicated page for exploring PostHog feature flags with live hedgehog GIF demos.

#### Hedgehog Feature Flags

Three demo flags — set them up in your PostHog project to see the hedgehogs come alive:

| Flag | Type | Values | Effect |
|------|------|--------|--------|
| `hog-spin` | Boolean | `true` / `false` | Shows a spinning hedgehog when enabled |
| `hog-dance` | Multivariate | `sonic`, `cgi`, `triple` | Each variant shows a different dancing hedgehog |
| `hog-action` | Multivariate | `run`, `sleep`, `swim` | Hedgehog running, sleeping, or swimming |

- Uses `posthog.onFeatureFlags()` to wait for flags before rendering
- Click variant buttons to override values client-side; GIFs update instantly

#### Feature Flags panel
- All project flags with Enabled / Disabled / variant badges
- Activate / Deactivate boolean flags or Switch multivariate flags
- Reload from server or Clear All Overrides

#### Flags Applied to You
- Active flags for the current session shown as green badges

### Experiments (`/experiments`)

A wizard for generating realistic experiment data in your PostHog project. Uses PostHog's **batch capture API** (`/batch/`) — each simulated user gets their own `distinct_id`, so your real session is never affected.

**How it works:**

For each simulated user, the wizard:
1. Pre-determines whether the user will convert (based on your configured rate)
2. Calls PostHog's `/decide` endpoint with the user's `distinct_id` — PostHog's own rollout rules assign the flag variant, no manual assignment
3. Sends events via `/batch/` in the correct order: `$identify` → `$feature_flag_called` (with the real variant) → conversion event (if applicable)

**Wizard steps:**

| Step | What you configure |
|------|--------------------|
| 1 | Select a feature flag — multivariate flags shown by default (toggle to include boolean flags) |
| 2 | Number of simulated users (1–500, default 50) |
| 3 | Conversion rate (1–100%, presets available, random default) |
| 4 | Conversion action (`pasture_purchase`, `pasture_signup`, etc.) — shows event name and full payload |

**Flag detection heuristic:** Multivariate flags (string values like `"control"`, `"test"`) are shown by default — these are always associated with experiments. Boolean flags are hidden by default but can be shown via the toggle in the section header.

**Progress phases:**
- 0–70%: PostHog evaluates each user's flag variant via `/decide`
- 70–80%: Building the event batch
- 80–100%: Sending to PostHog via `/batch/`

**Results view** shows:
- Total users, converted count, actual conversion rate
- Per-variant breakdown (dynamically built from whatever PostHog assigned)
- Full user table with username, PostHog-assigned variant, and ✓/— conversion status
- "View in PostHog →" link to your experiments dashboard

## Data & Privacy

All configuration (API key, host, settings) and user session data is stored in **`localStorage`** in the browser. Nothing is persisted on any server. Your API key is only ever sent to PostHog's ingestion endpoints.
